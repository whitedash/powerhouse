Roles & permissions

One row per capability, one column per role. Most sections have an Access toggle (enter & view) and a Manage toggle (act within). Four sections — Projects, Tasks, Support and Leads — replace the Access toggle with a three-way scope: All (every item), Assigned (only items assigned to / owned by the user), or None. Scope governs which items are visible; Manage governs whether the user can act on what they can see. Scope is enforced — a scoped user can't reach an off-scope item by direct URL, not just by list.

Super Admin bypasses this matrix entirely. It always holds every permission at full scope and can never be locked out, so it has no editable controls — its column is shown for reference only (scopes read All, locked). The matrix governs every other role.

Legend & notes

How to read this matrix
Access enter / view a section Manage act within a section AllAsgnNone scope (visibility) Composes stacks with scope Danger high-stakes PII personal data On not editable
  • Three-way scope (All / Assigned / None) replaces the on/off Access toggle on four sections. Scope governs which items are visible; Manage governs whether the user can act on them. "Assigned" means, per section:
    • projects.access — I'm a member of the project (lead, member or viewer)
    • tasks.access — tasks strictly assigned to me (the assignee — not ones I created and delegated)
    • support.access — tickets assigned to me
    • leads.access — leads assigned to me
  • Scope is enforced, not cosmetic. A scoped user can't reach an off-scope item by direct URL or ID — enforcement is on both the list query and per-item access, so "Assigned" is a real boundary, not just a default filter.
  • support.view_unassigned composes with the Support scope. Scope Assigned + this on = the agent's own tickets plus the unassigned intake pool (a self-serve agent — the Support Agent example). Assigned + this off = only tickets routed to them. With scope All the toggle is redundant (everything is already visible).
  • Super Admin bypasses the matrix. Always every permission at full scope, never lockable — its column is reference-only (scopes read All, locked).
  • account.self is always-on for every operator and is not shown as a toggle: own profile, password, personal notification preferences, My Work, global search and the dashboard.
  • The marked rows are the dangerous ones (red, ⚠). Destructive / financial / security / config capabilities — grant sparingly. forms.view_submissions is split out (PII) because it exposes data submitted through public forms.
  • Customers is a future scope candidate. It carries an account-manager assignment (customers.assigned_to), so it could adopt the same All / Assigned / None treatment later. It stays a binary Access/Manage section for now.
  • Migration safety. The Staff column is access-identical to today — all four scoped sections default to All, every Access/Manage is on, and every super-admin-only capability is off — with one deliberate change: webhook-retry moves into settings.integrations (super-admin-only).
