# Decision Log — Powerhouse

| Date | Decision | Rationale |
|---|---|---|
| May 2026 | Laravel + Vue SPA | Consistent with MyOrderPad; better suited to application logic than WordPress |
| May 2026 | Laravel Passport for OAuth 2.0 | Central auth server for all Whitedash products |
| May 2026 | MySQL | Consistent with existing stack |
| May 2026 | HTTPS for GitHub remote | No SSH keys configured on dev machine |
| May 2026 | Products table database-driven | Supports adding future products without code deploys |
| May 2026 | Powerhouse never commercialised | It is Apostolos's operating layer, not a product |
| May 2026 | Each product control panel investor-ready | Any product can be spun out independently of Powerhouse |
| May 2026 | Universal customer account via OAuth 2.0 | One Whitedash relationship per customer; brand identity |
| May 2026 | Multi-entity invoicing from day one | Future LTD companies must be supportable without schema changes |
| May 2026 | Commission rules use JSON config | Flexible for all models; new products need no schema changes |
| May 2026 | Security sprint before any customer data | FormRequests, Policies, headers, encrypted casts, rate-limit, audit log; SECURITY.md captures the deploy checklist |
| May 2026 | Session-based staff auth, not Passport | Passport is reserved for OAuth API (product control panels). Staff use Laravel's `web` guard. |
| May 2026 | Login throttle = 5 attempts per 15 min per (email+IP) | Spec is "5 per minute"; widened the window to 15 min — same allowance, blocks slow distributed brute-force, clears on successful login |
| May 2026 | `Model::preventLazyLoading` enabled in non-production | Forces explicit eager loads. Catches N+1 in development and CI without slowing production |
| May 2026 | Sensitive billing fields encrypted at rest | `sort_code`, `account_number`, `account_name`, `qbo_access_token`, `qbo_refresh_token`, `two_factor_secret` cast as `encrypted`. Columns widened to TEXT. |
| May 2026 | `RedactSensitiveData` Monolog processor on stack | Anything matching password/token/secret/sort_code/etc keys is logged as `[REDACTED]` |
| May 2026 | PKCE (S256) enforced on every `/oauth/authorize` request | Prevents authorisation-code interception. Spec called for a `code_challenge_method` column update; Passport 13's `oauth_clients` table has no such column, so enforcement moved to a `RequirePkce` middleware that gates the authorize endpoint instead. Works for both confidential and public clients. |
| May 2026 | `hash_equals()` for every token / signature compare | Prevents timing attacks on cryptographic equality. Banned `==`/`===` for these values; documented in CLAUDE.md. Grep audit at sprint start found zero existing violations. |
| May 2026 | `FileUploadService` centralises all uploads | UUID filenames, real-byte MIME check, EXIF stripped via Intervention re-encode to JPEG 85, SVG sanitised, stored on a dedicated `private` disk. Defends against MIME spoofing, path traversal, and embedded XSS payloads. |
| May 2026 | `webhook_events` table for idempotency | Unique on `(source, event_id)`. Every webhook handler must consult `WebhookIdempotencyService` before processing. |
| May 2026 | Rate limiting on listing endpoints (`throttle:60,1`) | `/customers`, `/invoices`, `/referrers` capped at 60/min/user. Slows credential-stuffing-style scraping. Mass-export detection (`DetectMassExport` listener, 50/10min threshold) fires `security.mass_export_detected` + emails super admin. |
| May 2026 | `App\Rules\NotInternalUrl` validation rule | Prevents SSRF. Rejects any URL whose host resolves to loopback, RFC1918 private space, link-local (incl. AWS metadata 169.254.169.254), CGNAT, or IPv6 ULA / link-local. Mandatory on every user-supplied URL. |
| May 2026 | Invoice edit allowed for draft / sent / overdue | Paid and void invoices remain immutable. Sent invoices may need correction (wrong VAT, typo in line item, address mistake) before payment is received — locking them at draft-only forced staff to void + recreate, losing the audit chain. Policy widened in `InvoicePolicy::update()`. |
| Jun 2026 | Public submit-ticket (hub Phase 3) | `/support` lets a guest open a ticket without an account. `support_tickets.customer_id` made **nullable** (+ `guest_name`/`guest_email`/`guest_phone`) — guest tickets carry submitter details instead of a customer FK. A shared `App\Services\TicketIntakeService` is the single intake path (used by both the public controller and a new `create_ticket` WorkflowEngine action): it creates the ticket + first `SupportMessage` (sender_type=customer, source=web) + an admin triage Task (assigned to the resolved triage user — `tasks.assigned_to` is NOT NULL, so a truly unassigned task isn't possible without a schema change; it lands in the triage queue), all in one transaction, then sends the `SupportTicketReceived` acknowledgement **synchronously** after commit (no queue-worker dependency). The triage Task's `created_by` resolves to `config('support.triage_user_id')` if that user exists else the first super_admin — never a magic id — so the in-transaction Task insert can't FK-fail and drop a guest's ticket. The Task soft-links to the ticket by reference (no `tasks.ticket_id`). Anti-abuse: honeypot + route throttle + **Cloudflare Turnstile** (server-side siteverify via the Http client; `services.turnstile.bypass` skips it in tests/keyless-local only, never prod). Support placeholders flipped live (header nav, landing door, KB "still need help?"); `/apply` stays "Soon". No product picker on the public form in v1 (service still accepts an optional product_id). | 
| Jun 2026 | Public knowledge base (hub Phase 2) | `Public\KnowledgeBaseController` serves `/kb` (index, paginate 20, title+content search, category filter) and `/kb/{slug}` (throttle:60,1; simple every-hit `views++`). Every query is scoped to `is_public && is_published` — the public IDOR-equivalent, so internal/unpublished articles 404 on direct slug access. Article bodies render via a new `App\Services\KbContentService`: `render()` detects HTML-vs-Markdown (same logic as staff HelpController), `renderSafe()` additionally runs the output through **`symfony/html-sanitizer`** with a strict allow-list (safe elements only; link schemes limited to http/https/mailto; anchors forced to `rel=nofollow noopener noreferrer target=_blank`) before it reaches `v-html` on the public page. The Phase-1 "Knowledge base" placeholders (header nav + landing door) went live and the featured-help strip (top 6 by views, self-hiding) was restored on the landing. `/support` (Phase 3) and `/apply` (referral Phase 2) stay "Soon". Staff Help still uses its own private renderer — unifying it onto KbContentService is a tracked follow-up. No schema change. |
| Jun 2026 | Public hub front door at `/` | The hub had no logged-out entry point — `/` was the internal staff dashboard. Added a `PublicLayout` + `Public/Landing` (standalone Inertia on the root design tokens, matching Login/ProposalView). `/` is now a public `LandingController` that branches by auth state: guests see the marketing landing; authenticated staff/super_admin redirect to the internal dashboard, referrers to `/referrer/dashboard`. The dashboard moved from `/` to `/dashboard` — its route NAME stays `internal.dashboard`, so every `route('internal.dashboard')` caller is unaffected (only the two literal `'/'` references — InternalLayout's Overview nav + a DashboardController fallback — were updated, and StaffLoginController's default destination switched from `'/'` to `route('internal.dashboard')`). No schema change. KB / Support / Become-a-partner render as inert "coming soon" until their phases land; the featured-help strip is deferred to Phase 2. Confirms public pages render via Inertia, not Blade. |
| Jun 2026 | Referral attribution Phase 1 (spine) | Extended the existing referral infra rather than rebuilding. `referrers` got a unique 8-char Crockford base32 `referral_code` (one universal `/r/{code}` link; backfilled + minted on create). New `referral_clicks` logs every valid-code hit; `AttributionService` resolves **last-touch within a 60-day window**, **new-customers-only**, **self-referral blocked**, writing ONE immutable row to **`customer_referrals` extended in place** (this is the spec's "referrals" table — not a new one; added lead_id/click_id/product/source/campaign/converted_at). Public lead path now captures the referrer (`leads.referrer_id`/`referral_code`) and `LeadController::convert()` calls the service (it previously dropped referral identity). Dead, FK-less `customers.referred_by` **dropped** (grep-confirmed no readers). New `AttributionSource`/`ProductKey` PHP enums. Internal `/referrals` ledger + referrer-portal link/click stats. Commission generation deferred to a later phase (no commission schema change). Cookie/?ref capture on external product sites + the `/api/referrals/attribute` ingest are Phase 3. |
| Jun 2026 | Additive `people` ↔ companies layer for multi-company ownership | "One person owning multiple companies" needed a cross-company human identity. Rather than refactor the ~55-file `contacts` surface, we added a NEW layer alongside it: a `people` table + a `customer_person` M:N pivot (role + job_title on the pivot, compound-unique on `(customer_id, person_id)`). `customers` stay one-company; `contacts` keep their NOT NULL `customer_id` one-to-many and their recipient-resolution role. A nullable `contacts.person_id` (set null, no v1 backfill) optionally links an operational contact to a person. `App\Enums\PersonRole` is the single source of truth for pivot roles (DB column is a plain string) — deliberately avoiding the value-list triplication that `contacts.role` suffers. `contacts` email-uniqueness relaxed from global to per-`customer_id` so one human can be a contact at several companies. No `is_primary` on the pivot in v1 (avoids overlap with `contacts.is_primary`). |
| Jun 2026 | Deal Registration — Sprint 1 (register → review → protect) | Partners register prospective deals from the portal; staff review; on approval a **fixed 90-day** protection window opens with the **clock starting at APPROVAL** (not registration). A registered deal is just a `Lead` with a new `referral_status` lifecycle (`pending_review`/`approved`/`rejected`/`expired`, PHP enum `App\Enums\ReferralStatus`) kept **separate from the pipeline `status` enum** — NULL means "not a deal-registration", so every existing manual/cookie-attributed lead is untouched. New nullable `leads` columns: `referral_status`, `registered_at`, `protected_until`, `reviewed_by`, `reviewed_at`, `review_notes`, `referral_consent_at` (indexed on `referral_status` + `protected_until`). All logic lives in `DealRegistrationService`: **register()** stamps `referrer_id` from the AUTHENTICATED referrer (never from input), sets `source=referral`, `status=new`, `referral_status=pending_review`, `registered_at`/`referral_consent_at=now`, and records the chosen product in `source_detail` (no product column added in Sprint 1); **approve()** sets `protected_until = now + config('referrals.protection_days', 90)`; **reject()** stores the reason in `review_notes`. **Dedup / net-new** is enforced at registration: match email → else phone → else company against existing customers/contacts AND leads; a match that is NOT the referrer's own prior registration throws a `ValidationException` with a deliberately **non-revealing** message (never leaks the existing record). Authorization via `LeadPolicy` (`register` = active referrer; `review` = staff) + `StoreReferralDealRequest` (required GDPR consent checkbox). Referrer portal gains a **Referrals** tab (own deals only, 20/page, IDOR-safe) + a "Register a deal" slide-over (product picker; self-serve product — `config('referrals.self_serve_slug')` — also shows the referrer's share link). Internal Leads gains a **Referral review** queue (Approve / Reject-with-reason); `pending_review`/`rejected`/`expired` deals are **filtered out of the sales kanban + KPIs** so sales only works approved/house leads, and approved deals show a "Protected — {referrer} until {date}" badge on the card + detail. Attribution spine unchanged except one guard: `AttributionService::attributeFromLead` now skips when `referral_status` is `rejected`/`expired` (approved + null attribute as before). |
| Jun 2026 | Deal Registration — Sprint 2 (protection expiry) | Added `referrals:expire-protections` (`App\Console\Commands\ExpireDealProtections`): selects leads where `referral_status = approved AND protected_until < now AND status != won AND customer_id IS NULL` and flips them to `expired` (one `DB::transaction` + `activity_log` `referral.deal_expired` per row; `protected_until` left as the historical date for audit). `chunkById(200)` keeps memory flat; **idempotent** — once a row is `expired` it no longer matches, so re-running is a clean no-op (covered by a test). Won/converted deals are explicitly excluded (the referrer earned them); pending_review / rejected / NULL leads are untouched. Registered in `routes/console.php` to run **daily at 03:30 Europe/London** (`withoutOverlapping()->runInBackground()`), 30 min after the `support:close-inactive` small-hours sweep — same pattern as the ~11 existing daily/interval schedules there (recurring + subscription invoices, reminders, suspensions, ticket auto-close, domain/website/WordPress syncs, overdue-notifications, health-cache warm), so a cPanel `schedule:run` cron is already presumed in place. `--dry-run` flag mirrors the other sweep commands. No schema/migration, no frontend. |
| Jun 2026 | Commission Engine — Sprint 1 (invoice-paid accrual) | Commissions now accrue automatically when an invoice is **paid** — the single settle point `StripeService::markInvoicePaid` (covers Stripe webhook `checkout.session.completed` + `payment_intent.succeeded` **and** the portal success-confirm, plus recurring subscription invoices). A new `CommissionService::accrueForInvoice` loads the paid invoice's lines (product_id lives on the **lines**, not the header), finds the customer's immutable `customer_referrals` attribution → an **active** referrer, groups lines by product, and writes one `pending` `commission_ledger` row per product via a **source-agnostic `accrue()` core** (so a future external/HMAC ingest reuses it unchanged). **5 decisions:** **(1)** The rule resolver + commission math were extracted from `MaavelusStatementService` into a shared `CommissionRuleResolver` + `CommissionService::calculate()`; Maavelus was refactored onto them with **zero behaviour change** (a feature test pins identical output). **(2)** The calculator gained **flat amount** (`config.flat_amount`, takes precedence over %) and a **per-rule recurring duration cap** (`config.recurring_months`; null/0 = lifetime); `recurring_tiered` stays stubbed at 0 (Sprint 2). **(3)** Maavelus stays on its own statement flow and is **excluded** from the invoice engine via `config('referrals.commission_excluded_slugs')` (default `['maavelus','maavelus-hospitality']`, mirroring `self_serve_slug`'s config-driven shape) so its revenue is never double-counted. **(4) Idempotency** is belt-and-braces: a new **unique index** `commission_ledger (invoice_id, referrer_id, product_id)` (invoice_id NULLable → MySQL NULLs distinct, so Maavelus null-invoice rows don't collide) **plus** an application-level already-accrued check — webhook retries / multi-path settles never double-credit. One-off accrual fires once per customer×product (`trigger=onboarding`); recurring fires per subscription-invoice (`trigger=invoice_paid`) until the cap. **(5)** The accrual is called at the **end of `markInvoicePaid`, after commit, only on the real unpaid→paid transition**, wrapped in `try/catch + report()` — a commission failure can never roll back or break the customer's payment. Approve/mark-paid lifecycle is unchanged (still manual via ReferrerController). Clawback (refund/churn) is Sprint 2. No frontend change — the portal already reads the ledger. |
| Jun 2026 | Commission Rules admin UI (internal) | A super_admin Settings surface (`/settings/commission-rules`, new SettingsLayout tab) to manage `commission_rules` — previously editable only by hand/seed. The form is a **faithful front-end to `CommissionService::calculate()`'s config contract**, exposing friendly inputs (not raw JSON): mode One-off vs Recurring, then percentage **or** flat amount (one-off → `type=one_off_pct`, `config{percentage}` or `{flat_amount}`), or a recurring percentage + duration Lifetime/N-months (recurring → `type=hybrid`, `config{recurring_percentage[, recurring_months]}`). `recurring_tiered` is **not exposed** (deferred/stubbed). `CommissionRuleService` translates inputs → type+config in a txn + activity_log; `StoreCommissionRuleRequest` validates (product required; at least one rate; percentages 0–100; flat ≥ 0; recurring_months positive int) + `CommissionRulePolicy` (super_admin). **OVERLAP GUARD:** the resolver picks one rule by ordering with no DB uniqueness, so the service **blocks creating/activating a second ACTIVE rule for the same (referrer_id, product_id) with an overlapping validity window** (inactive rules exempt) — resolution stays unambiguous. **EDIT SEMANTICS:** edits affect FUTURE accruals only (the engine computes at accrual time and ledger rows store their amounts); the form carries a note steering rate changes toward `valid_from`/`valid_until` versioning. Round-trip is tested (a rule created via the form produces config the calculator reads back to the expected amount). No schema change (`commission_rules` already existed); no migration. |
| Jun 2026 | Support Portal — Sprint 1 (SLA tracking + metrics) | First-response SLA tracking on support tickets, with **four locked decisions**: **(1) first-RESPONSE is the hard SLA** — `sla_breach_at` (already = created_at + per-priority hours) is reinterpreted as the first-response deadline; `first_responded_at` is stamped once, on the FIRST staff non-internal reply (`SupportSlaService::stampFirstResponse`, idempotent — a second reply or an internal note never moves it). **(2) Resolution time is MEASURED, not committed** — analytics shows avg RAW resolution (`resolved_at − created_at`, no pause), with no resolution target. **(3) Per-priority targets are CONFIG-DRIVEN** — the SLA_HOURS map moved out of TicketIntakeService into `config/support.php` (`first_response_hours`: urgent 4 / high 8 / medium 24 / low 72), read via `SupportTicket::firstResponseHours()` (single source; can later key on product/tier). **(4) Breach is COMPUTED ON READ** — `SupportTicket::slaState()` → `App\Enums\SlaState` (met = responded ≤ deadline; due = unresponded & in-window, with `slaRemainingSeconds()` countdown; breached = responded late OR unresponded past deadline). No stored breach flag, no sweep. New columns: `first_responded_at`, `reopened_at`, `reopen_count`. Reopen (resolved|closed → open) is centralised in `SupportSlaService::recordReopen`, hooked through the three paths (staff reply, status change, inbound-email reply) so they stay consistent — stamps `reopened_at` + increments `reopen_count` only on a genuine closed→open transition (awaiting_customer → open is not a reopen). Helpdesk index + show render an SLA badge (countdown / MET / BREACHED) from the derived state. AnalyticsController gains a support section (avg first-response, % within SLA, breach count/rate, avg raw resolution, reopen rate, volume by status/priority/product) + a panel in the analytics page. CSAT joins this panel in Sprint 2. |
